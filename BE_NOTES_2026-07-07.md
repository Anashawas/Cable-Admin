One server-side aggregate for the Users header + insights strip (don't pull the

### Field definitions & priority
| Field | Priority | Definition |
|---|---|---|
| `totalUsers` | high | All non-deleted users |
| `active` / `deleted` | high | Split by `isDeleted` (the real status signal; list has no `isActive`) |

> `byRole` counts must match the header tab badges exactly, and `active`/`deleted`

## A2. 🔴🔴 Server-side paged + filtered lists — Users **and** Stations

**Most important item today.** Replace "fetch the whole list → filter in the
browser" for **both** the Users list (~14k rows) and the Stations /
Charge-Management list.

### Pagination is **optional** (opt-in)
Support paging via query params, but when they are **omitted the endpoint returns
the full list** (current behavior) so nothing breaks. i.e. `page`/`pageSize` are
optional; if absent → return all. This lets us adopt paging screen-by-screen
without a hard cut-over.

### A2a. Users — `GET /api/users`
`GET /api/users?page=1&pageSize=25&search=&role=&city=&isDeleted=false&sort=createdAt_desc`

- **Auth:** Admin.
- `search` matches **name, email, phone, or id** (the admin has a dedicated
  phone-search field today — must be server-side).
- Filters: `role` (id), `city`, `isDeleted`.
- `sort`: at least `createdAt` and `name`, asc/desc.
- Keep the existing `UserSummaryDto` fields (id, name, userName, email, phone,
  city, role, isDeleted, isPhoneVerified, createdAt, userCars).

### A2b. Stations — `GET /api/charging-points`
Same optional-paging pattern with the station filters already used in the admin:
`search`, `type`, `city`, `status`, `brand`, `verified`, `plugType`, `sort`
(visitors/rating/name). Keep the existing station DTO fields.

### Paged envelope (both) — same shape as the loyalty admin endpoints
```json
{ "items": [ /* existing DTO */ ], "totalCount": 13987, "page": 1, "pageSize": 25 }
```
> When paging params are omitted, either return a plain array (as today) or this
> envelope with the full set — either is fine; just keep it consistent.

## A3. ⚠️ Dependency — reliable `createdAt` on users

# B. Offers (Create / Update)

## B1. 🔴 New field on offers — `pointsPriceValue` (cash value of the points)

When creating/editing an offer we now capture **three** distinct money/points values.
Today the API only stores two; we need the third persisted.

| Field | Meaning | Who it's for |
|---|---|---|
| `pointsCost` | Points the **user** spends to redeem the offer | user side |
| **`pointsPriceValue`** 🆕 | **Cash value those points represent**, derived from the active **conversion rate** (e.g. 100 pts ÷ 50 pts-per-JOD = **2 JOD**) | what the points are *worth* |
| `monetaryValue` | Fixed amount **Cable pays the provider** per redemption (the agreed deal) | Cable ↔ provider settlement |

> `pointsPriceValue` and `monetaryValue` are **not** the same: the first is the
> monetary worth of the points to the user (via the conversion rate); the second
> is the payout Cable owes the provider. Both must be stored.

### The points ⇄ price link (already implemented in the admin UI)
The admin form links `pointsCost` and `pointsPriceValue` **bi-directionally** using
the **default active `ConversionRate`** for the offer's currency
(`GET /api/conversion-rates/GetAllConversionRates` → `pointsPerUnit`):

```
pointsPriceValue = pointsCost / pointsPerUnit      // e.g. 100 / 50 = 2.00 JOD
pointsCost       = round(pointsPriceValue * pointsPerUnit)
```

### What we need from BE
1. Add nullable **`pointsPriceValue` (decimal)** to:
   - `ProposeOffer` request body
   - `UpdateOffer` request body
   - `OfferDto` response (list + detail)
2. **Persist** it as sent by the admin.
3. **Recommended:** validate/compute it server-side from the active conversion
   rate so FE and BE never disagree — if the client omits it, derive it from
   `pointsCost / pointsPerUnit`; if present, it may be stored as-is (admin may
   round). Reject only if wildly inconsistent (optional).
4. It should flow through to **settlement / transaction** records if you want
   points-value reporting later (nice-to-have, not blocking).

### Example payload (ProposeOffer)
```json
{
  "title": "Free coffee",
  "providerType": "ServiceProvider",
  "providerId": 42,
  "pointsCost": 100,
  "pointsPriceValue": 2.00,
  "monetaryValue": 1.50,
  "currencyCode": "JOD",
  "validFrom": "2026-07-08"
}
```

## B2. Notes / already available
- The **conversion-rate** catalog already exists
  (`GET /api/conversion-rates/GetAllConversionRates`, returning `pointsPerUnit`,
  `isDefault`, `isActive`, `currencyCode`) and is managed in the admin's
  *Conversion Rates* screen — no new work there; this requirement only reuses it
  to derive `pointsPriceValue`.
- FE is already sending `pointsPriceValue` in the create/update payloads and
  reading it back from `OfferDto` (typed as optional). It's a no-op until BE
  stores/returns it, so shipping order is safe.

# C. Settlements

> **Context:** The admin Settlements screen already shows summary KPIs, per-provider
> settlement cards, status workflow (Pending → Paid / Disputed), wallet
> management (deposit/refund/adjust + credit limit), and money-flow breakdown.
> These are the gaps found while auditing it. The FE has already been polished
> (surfaced unused summary fields, added pending-aging flags, error states,
> removed dead code); the items below need BE.

## C1. 🔴 Settlement transaction line-items — `GET /api/offers/GetSettlementTransactions`

The single biggest gap. A settlement shows **counts and totals**
(`partnerTransactionCount`, `offerPaymentAmount`, `partnerCommissionAmount`, …)
but there is **no way to see the underlying transactions** that produced them.
Admins cannot verify or resolve a **dispute** without the line items.

- Proposed: `GET /api/offers/GetSettlementTransactions?settlementId={id}` →
  the partner charges + offer redemptions in that settlement's period, each with:
  user (id + name), amount, points, offer/partner reference, code, status, date.
- **Note:** `GET /api/offers/GetProviderTransactions` already exists but is scoped
  by provider only (not by settlement period) and is **not currently used** by the
  admin. If it can be scoped to a settlement's period/id, that's enough — no new
  endpoint needed.

## C2. 🟠 Summary additions on `SettlementSummaryDto`

The summary endpoint (`GetSettlementSummary`) omits two totals the admin now
derives client-side from the loaded rows (works, but wrong once the list is paged):
- `totalOutstandingAmount` — Σ `outstandingAmount` (commission still owed after wallet).
- `totalDisputedAmount` — Σ |netBalance| where status = Disputed.

Also currently unused-but-present and worth surfacing if cheap:
`totalPartnerTransactionAmount` (total user payments), `totalPointsAwarded`,
`totalPointsDeducted`.

## C3. 🟠 Bulk status update — `PUT /api/offers/UpdateSettlementStatusBatch`

Mark **multiple** settlements Paid/Disputed in one call (e.g. "settle all pending
for this provider / this week"), instead of one PUT per settlement.

## C4. 🟠 Export settlements (CSV) — `GET /api/offers/GetSettlements?format=csv`

Streamed CSV honoring the current filters (year/week/type/status/search) for
finance/ops. Columns: provider, owner, period, partner tx/amount/commission,
offer tx/payment, netBalance, walletApplied, outstanding, status, paidAt.

## C5. 🟡 Aging / due date

Add a `dueDate` (or settlement-generated date we can age against) per settlement
so the admin can flag **overdue** pending settlements. The FE already shows
"pending N days" from `createdAt`; a real due date would make overdue accurate.

## C6. 🟡 Server-side paging/filter for settlements

Same optional-paging pattern as **A2** — today the screen loads a whole year and
filters/paginates client-side, and fires a **per-row wallet-balance query**
(N+1). A paged `GET /api/offers/GetSettlements` (+ a batched wallet-balance
lookup) would remove both.

## C8. 🟠 Enrich wallet transactions with the end user + refund action

The wallet-history rows (`WalletTransactionDto`) only carry `createdByUserName`
(the **admin/system** actor) and a free-text `note` like
*"Batch refund for 1 expired transactions (IDs: 4)"*. For system-generated types
(`SettlementDeduction`, `CommissionDeduction`, `CommissionRefund`,
`OfferPaymentCredit`, `OfferPaymentRefund`) the admin needs to know **who the
underlying transaction belonged to** and act on it.

Add to `WalletTransactionDto` (and the `GetWalletHistory` response):
- `relatedUserId` + `relatedUserName` — the **customer** whose offer/partner
  transaction produced this wallet entry (not the admin).
- `relatedTransactionIds` — the underlying offer/partner transaction id(s)
  (structured, instead of embedding "IDs: 4" in the note).
- Optionally the underlying transaction detail (code, amount, points, status, date).

**Refund action (if business allows):** an endpoint to refund a specific
transaction back to its user — e.g. `POST /api/offers/RefundTransaction`
`{ transactionId }` — plus a `canRefund` flag per wallet row so the admin knows
when it's still refundable.

> FE is already forward-ready: `WalletTransactionDto` has optional
> `relatedUserId` / `relatedUserName` / `relatedTransactionIds` / `canRefund`, the
> wallet-history row renders a clickable **user chip** (→ user profile) and a
> **Refund** chip when `canRefund` is true. All no-ops until BE returns them.

## C7. 🟡 Generation cadence / recompute

Confirm **how settlements are generated** (scheduled job? which day/cadence?) and
give admins a **"recompute period"** trigger for when transactions change after a
settlement was generated. Also expose `periodType` (weekly/monthly) so the UI can
stop assuming weekly (`W{week}` is currently hardcoded).
